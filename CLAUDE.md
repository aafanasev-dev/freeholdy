# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A FastAPI service (`app/`) that orchestrates Docker containers behind nginx + Let's Encrypt on a single VPS, exposing each as `*.your_domain.com`. A standalone CLI (`cli/fhcli.py`) wraps the HTTP API; it keeps its own `.env` and is not imported by the server, but **shares the project's single venv** — it re-execs itself under `<repo>/venv/bin/python`, so it runs unactivated and through a symlink.


## System components vs pet projects

freeholdy manages two distinct layers:

**System infrastructure** — started outside the freeholdy API, provisioned by `install.sh` (the one-command bootstrap) and managed by the OS:
- `nginx` (system service)
- `certbot` (system service)

**Managed pet projects** — created by a **deploy** (`fhcli deploy` → chunked upload or `POST /git/add`; both auto-create the row) or `fhcli plugin-add`, tracked in SQLite, proxied by nginx. Includes `type: "system"` projects (webui) that are hidden from the web UI but are otherwise normal managed projects.

**Upgrading an installed server is `update.sh`, not `install.sh`** (repo root). `install.sh`'s resume log marks `fetch_source` DONE, so re-running it never pulls. `update.sh` lists `origin`'s `main` plus every tag (each annotated with the `version.json` it declares — peel refs with `^{commit}`, an annotated tag rev-parses to the tag object), asks which to take, then: delete the `webui` + `freeholdy-help` projects if present → `systemctl stop freeholdy` → `git reset --hard` + `git clean -fd` (**never `-x`**: `.gitignore` is what preserves `.env`, `data/`, `projects/` and the venvs) → `configure.sh` (the shared venv builder: rebuilds on interpreter drift, reinstalls only when a hash of `requirements.txt` stored inside the venv changes) → back up the DB + run `migrate_db.sh` → start + poll `/health` → re-add the two plugins and poll `GET /projects/{n}/status` until the build leaves `running`. The delete/re-add is **required**, not incidental: `plugins/webui/install.sh` copies `webui/` out of the repo into the build context at install time, so a pull alone never reaches those containers, and `POST /plugins/{n}/add` is a 409 while the project exists. It mints a temporary API token and revokes it in an EXIT trap, so existing tokens (and the operator's web-UI login link) keep working.

## Common commands

Server (run from repo root; `bash configure.sh` builds `./venv` — one venv for the server and the CLI):
```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload   # dev
python scripts/generate_token.py generate --name "label"   # mint API token (printed once)
python scripts/generate_token.py list | revoke --id N
```

CLI (see `cli/README.md`; shares `./venv`, no activation needed — it re-execs into it.
`install.sh` also links it to `/usr/local/bin/fhcli`, so `fhcli …` works box-wide):
```bash
./cli/fhcli.py health | projects
./cli/fhcli.py plugins                      # list available plugins
./cli/fhcli.py plugin-add PLUGIN PROJECT    # create a project from a plugin
./cli/fhcli.py deploy PROJECT PATH-OR-GIT-URL   # auto-create + provision + build/run (local path or git URL); re-run to redeploy
./cli/fhcli.py deploy PROJECT SRC --env FILE    # …storing FILE's vars before the first container start
./cli/fhcli.py versions PROJECT             # list blue/green versions (active/inactive/archived)
./cli/fhcli.py rollback PROJECT VERSION     # roll back to an inactive/archived version
./cli/fhcli.py set-backup-limit PROJECT N   # cap archived versions (default 5)
./cli/fhcli.py env-get PROJECT [-s SVC]     # download the stored .env file (stdout)
./cli/fhcli.py env-set PROJECT FILE [-s SVC]  # upload it ("-" = stdin); saved only
./cli/fhcli.py restart PROJECT              # recreate container(s), no rebuild → applies env
./cli/fhcli.py logs PROJECT [-n N] [-s SVC] # last N lines the container printed
./cli/fhcli.py volumes PROJECT              # list docker volumes + measured sizes
./cli/fhcli.py volume-download PROJECT VOL [-o FILE]  # tar a volume out (chunked)
./cli/fhcli.py volume-upload PROJECT VOL FILE         # replace a volume's contents with a tar
./cli/fhcli.py remove PROJECT [--keep-volumes]        # teardown; volumes go too by default
```

No test suite, linter, or formatter is configured — do not invent commands for them.

## Architecture

**Deploy → detect → DB → Docker → nginx → certbot.** There is no separate create step: a **deploy** (a chunked upload's `POST /projects/{name}/upload/complete`, or `POST /git/add`) **auto-creates** the project row if it doesn't exist yet (`projects.py::_get_or_create_project`) and then does all the wiring — writes files into the one per-project directory, auto-detects the deploy mode, and launches build + run. A deploy with no manifest leaves an empty `deploy_mode:"pending"` row (a plain file sync). Understanding the upload flow (`projects.py::upload_complete` / `_autoprovision`) is the fastest way into the codebase.

The deploy mode is **not** chosen at create — it is auto-detected by scanning the uploaded project root (`projects.py::_detect_manifest`): a `docker-compose.yml` (also `compose.yaml`/`compose.yml`) selects compose mode and **wins over** a `Dockerfile`; a bare `Dockerfile` selects dockerfile mode. Uploading the other manifest type onto an already-provisioned project is rejected (400 — remove + recreate to change mode).

**`dockerfile`** — a single container per project (detected from a `Dockerfile`):
1. `projects.py::provision_dockerfile` allocates one free port from `PORT_RANGE_START..END`, assigns subdomain `{name}.{domain}` (plugins may override via `domain_prefix`), and sets deterministic Docker names `freeholdy_{name}` / `freeholdy_{name}:latest`. It is idempotent — re-uploads keep the existing port/subdomain.
2. `app/services/nginx_service.py::setup_nginx` runs a **three-pass nginx setup**: HTTP config → nginx reload (ACME challenge) → `certbot certonly --nginx` per subdomain → SSL config → nginx reload. SSL success is stored on `Project.ssl_enabled`.
3. The container port comes from the Dockerfile's `EXPOSE` (`scan.exposed_port`; the upload is rejected 400 if absent). `scan.uses_websocket` scans the same text; if WebSocket usage is detected, `Project.websocket` is set and the nginx SSL config is regenerated with upgrade headers.
4. **Build + run is launched automatically by the provisioning upload** (`projects.py::launch_deploy` → `deploy_service.bluegreen_deploy`, job_key = the stable base `freeholdy_{name}`) and streamed over `WS /projects/{name}/deploy` — the same unified deploy path git uses; re-upload to redeploy. There are **no** `/build` or `/start` endpoints. The remaining `app/routers/container.py` calls (`/projects/{name}/stop|status|abort|ssl|domain`) operate on the `Project` row via `app/services/docker_service.py`. **Exec is a WebSocket, not REST:** `WS /projects/{name}/exec` bridges an interactive `docker exec -it` shell on a pty (`interactive_service.run_exec_session`; auth → ready → `stdin`/`stdout`/`resize` frames → exit). An optional `?cmd=` overrides the default shell.
5. **Deploys are blue/green with archived backups** (`app/services/deploy_service.py`). Every dockerfile deploy builds a **new version** `freeholdy_{name}:v{N}` in container `freeholdy_{name}_v{N}` on its own loopback port, runs it, then switches nginx to it (`write_ssl_config`/`write_http_config` — a pure port re-point) **only after** the build succeeds and the container is verified running; a failed build never takes the live site down. The build+run is a docker subprocess job; the nginx switch + version bookkeeping run as Python post-steps in a background thread, both streamed to one log registered (via `register_external_job`) under the stable base job key `freeholdy_{name}` — so the existing `WS /projects/{name}/deploy` shows the whole thing. `Project.container_name/image_name/local_port` always track the **active** version (so status/exec/nginx keep working). Each deploy creates a `ProjectVersion` row: one **active** (running, nginx points at it), at most one **inactive** (previous version, container `docker stop`ped but kept for fast rollback), and 0+ **archived** (image kept, container removed, port freed) capped by `Project.backup_limit` (default 5; oldest image `docker rmi`'d after a successful deploy). The first deploy reuses the port provisioned by `provision_dockerfile` (no switch); re-deploys allocate a fresh green port and switch. Version endpoints (`app/routers/versions.py`) serve **both modes**: `GET /projects/{name}/versions` (active/inactive/archived list + counts), `PUT /projects/{name}/backup-limit` (set + prune now), `POST /projects/{name}/rollback` (make an inactive/archived version active again — dockerfile: `docker start` for inactive, `docker run` from the retained image for archived; compose: snapshot restore + re-provision + `up` on retained tags — then re-shuffle statuses; streams over the same `WS /projects/{name}/deploy`). Plugin installs and git deploys go through the same `launch_deploy` dispatch, so they create version 1 via the same path in either mode.

**`compose`** — a multi-container stack (detected from a `docker-compose.yml`):
1. The unified upload calls `compose.py::provision_compose`, which parses the compose file, allocates a loopback port per exposed service, creates a `ComposeService` row for **every** service, writes a `docker-compose.override.yml` pinning container names + port bindings, and runs nginx/SSL setup for each exposed service. A service is **exposed** (`ComposeService.exposed`) iff it publishes a **TCP** port — it gets a loopback binding, subdomain, and nginx vhost. Services with no TCP port (UDP-only, e.g. the jitsi-meet plugin's JVB on UDP 10000; host-networking, e.g. outline's shadowbox; or internal-only, e.g. nextcloud's db/cache) are **unexposed**: their row has NULL `subdomain`/`local_port`/`container_port` and no nginx endpoint, but they are still tracked so the web UI shows their container status and offers per-service exec. Their original host bindings pass through the compose merge untouched. WebSocket detection runs per-service (scans that service's YAML block + name).
2. **Build + up is launched automatically by the provisioning upload** (`projects.py::launch_deploy` → `deploy_service.compose_bluegreen_deploy`, job_key = `compose:{name}`) and streamed over `WS /projects/{name}/deploy`; re-upload to redeploy. There are **no** `/compose/build` or `/compose/up` endpoints. The remaining lifecycle calls (`/compose/down|status|abort`) run `docker compose -p {name} -f docker-compose.yml -f docker-compose.override.yml`.
3. **Compose deploys are versioned too, but build-first with a brief switch** (`deploy_service.compose_bluegreen_deploy`) — true side-by-side blue/green is impossible for a stack in general (stacks bind host ports themselves, some use host networking, named volumes are shared). Each deploy: `docker compose build` + `docker pull` of registry images run **while the old stack keeps serving** (a failed build/pull never touches the live site), then each service's resolved image is retagged `freeholdy_{name}_{service}:v{N}` and pinned via a generated `docker-compose.images.yml` (a third `-f`), then a short `down` + `up -d --no-build` switches over (seconds; images already local). On a successful switch the whole project dir is snapshotted to `{DATA_DIR}/versions/{name}/v{N}/` (outside `PROJECTS_DIR`, which git deploys wipe) and a `ProjectVersion` row is written — with NULL `image_name`/`container_name`/`local_port` (per-service tags are deterministic; ports live on `ComposeService`). Compose version statuses are **`active` | `archived` only** (no stopped-container `inactive` tier — `down` removes containers); archived versions keep their image tags + snapshot, capped by `backup_limit`. The multi-phase job registers under the same `compose:{name}` key (`register_external_job` with a swappable process via `update_job_process`), so status/abort endpoints and the deploy WebSocket work unchanged; a failed switchover `up` triggers a best-effort re-`up` of the previous version from its snapshot. **Rollback** (`POST /projects/{name}/rollback`, same endpoint as dockerfile) downs the current stack, restores the snapshot into the project dir, re-runs `provision_compose` (which preserves custom domains **and** prior auto-subdomains, so plugin `domain_prefix` schemes survive), and `up`s the retained v{N} tags — named-volume **data is not rolled back**, only code + images. Startup (`app/main.py` lifespan) runs `deploy_service.backfill_compose_versions()` to give pre-versioning compose projects an active v1 (retags running containers' images + snapshots), mirroring `migrate_db.sh`'s dockerfile v1 backfill (which also makes `project_versions.image_name/container_name` nullable on upgrade).
4. Per-service exec — `WS /projects/{name}/services/{service}/exec` bridges an interactive `docker exec -it` shell into one service's `freeholdy_{name}_{service}` container (same `interactive_service.run_exec_session` as the dockerfile route), keyed `exec:{name}:{service}` so it never clobbers the stack's `compose:{name}` lifecycle job.

**Plugins** — pre-packaged project templates in `plugins/{name}/`:
- Each plugin has a `plugin.json` manifest: `name`, `description`, `deploy_mode`, `container_port` (dockerfile only), `type` (`user`|`plugin`|`system`), optional `domain_prefix`.
- A plugin may ship an optional `ABOUT.md` (Markdown) — long-form detail shown in the web UI's plugin panel. It is read by `plugin_service` into the plugin's `about` field, surfaced on `GET /plugins`, and is **not** staged into the build context. Absent → the UI falls back to `description`.
- `type: "system"` plugins (e.g. `webui`) are hidden from the web UI but are otherwise normal managed projects — created/deleted via the standard API.
- `POST /plugins/{name}/add` provisions the project (nginx/SSL via `provision_dockerfile` / `provision_compose` — the same service functions the unified upload calls, not the HTTP upload endpoint) then launches an async build+run job. The response always carries a `ws_path` — clients connect to `WS /plugins/{plugin}/install/{project}` to **stream the build log live** (`interactive_service.stream_job` tails the running job and sends an `exit` frame when it finishes; the build itself is a normal background job, so it survives a client disconnect and a reconnect re-streams it). A plugin may ship an `install.sh` that runs in two phases: `pre` (synchronous, before compose up — generate secrets) and `post` (background thread, after containers start — configure via REST API).
- **Interactive installs** — `"interactive": true` in `plugin.json` (requires an `install.sh`; e.g. `nextcloud`) makes the install prompt the user over the same install WebSocket. `POST /plugins/{name}/add` stops after staging (returns `job.status: "waiting_interactive"` + `ws_path`); the client connects to `WS /plugins/{plugin}/install/{project}`, authenticates with a first frame `{"type":"auth","token":…}`, and exchanges `stdin`/`stdout` JSON frames while install.sh runs on a pty (`app/services/interactive_service.py`; echo disabled — clients echo locally). On exit 0 the server launches the follow-up provision job (dockerfile: build+run; compose: `provision_compose` + up + `post`) and **streams it over the same socket**, so the `exit` frame reports the *build* result (no status polling). Disconnecting mid-install.sh kills the script and leaves the project pre-install; reconnecting re-runs install.sh if nothing is built yet, otherwise re-streams the running build (`fhcli plugin-add` resumes on 409). Only the `pre` phase is interactive for compose plugins.
- **nginx extras** — a plugin (or any project) may ship an `nginx-extra.conf`: staging copies it into the project dir like any other file, and `nginx_service.generate_ssl_config` inlines its contents into **every SSL `server {}` block** of that project at render time (`_load_extra_config` re-reads it on each regeneration — `/ssl` re-issue, websocket regen, custom domains all keep it). HTTP (port 80) blocks never get it. Used by `nextcloud` for `client_max_body_size 10G`, HSTS, and the `.well-known/{card,cal}dav` redirects.
- Discovery and staging live in `app/services/plugin_service.py`; the router is `app/routers/plugins.py`.

**Environment variables** — a `.env`-format file per project, stored in the DB (`ProjectEnvFile`, one row per scope) and injected at container start:
- Scopes: `service_name=""` is the project-level file — for a dockerfile project that **is** the container's environment; for a compose project it is shared by every service. A non-empty `service_name` is that one compose service's file, and its values **win** over the shared ones. Endpoints are `GET|PUT|DELETE /projects/{name}/env` and `.../services/{service}/env` (`app/routers/env.py`, mounted under the same `/projects` prefix as the other five routers).
- **Save-only.** A `PUT` stores the file and returns; it never touches a container. The values land on the container's **next start**, with no image rebuild — `POST /projects/{name}/restart` (`projects.py::launch_restart`, mode-dispatching) recreates the container(s) from the images they already run: dockerfile → `docker rm -f` + `docker run` the active version's image; compose → regenerate the override, then `up -d --no-build` on the pinned v{N} tags (`deploy_service.compose_restart`), so only the services whose env actually changed are recreated. **A restart never builds, so it refuses when there is nothing to start**: the dockerfile branch 400s without a container/image, and the compose branch 400s naming the services whose image is absent (`deploy_service.compose_missing_images` — the pinned v{N} tags when a pin file exists, else compose's resolved/default names, filtered by `docker_service.image_exists`). Without that guard a restart on a project whose first deploy failed would `down` the stack and leave it down with docker's bare `No such image: {project}-{service}`; the same check runs before a volume restore, which also ends in `up --no-build`. Checking images rather than version rows keeps pre-versioning stacks (no rows, good images) restartable. `EnvResponse.applied` is False while the stored file is ahead of what is running — it drives the web UI's "restart to apply" banner and the CLI's hint.
- **Parsing and materializing live in `app/services/env_service.py`.** `parse` accepts dotenv (comments, blank lines, `export ` prefix, single/double quotes) and rejects a bad key or a multi-line value with the offending line number (surfaced as a 422 by a `validate_env_content` field validator). `materialize` renders each scope to a normalized `KEY=value` file under `{DATA_DIR}/env/{project}/` (`_project.env`, `svc-{name}.env`, mode 0600) — **outside `PROJECTS_DIR`**, because git redeploys, compose rollbacks and teardown all wipe the project dir. Empty content writes no file, so a project with no env produces byte-identical docker commands to before the feature existed.
- Injection is `docker run --env-file` for dockerfile projects and absolute `env_file:` entries in the generated compose override (project file first, service file second — compose applies them in order, later wins). Materializing happens inside the existing `SessionLocal()` block of `bluegreen_deploy` / `rollback_to_version` / `compose_bluegreen_deploy`, in `_compose_rollback_job`, in `provision_compose`, and in `launch_restart` — every path that starts a container.
- **A deploy may carry the env with it, and that is the only way to reach the *first* container start.** `PUT .../env` is save-only, so a project deployed and started before its env exists boots without one. Both deploy transports therefore accept an optional `env` (dotenv text) in their request body — `POST /projects/{name}/upload/complete` (`UploadCompleteRequest`) and `POST /git/add` (`GitAddRequest`) — validated by the same `schemas.validate_env_content` as `SetEnvRequest`. `projects.py::apply_deploy_env` stores it **before `_autoprovision`** (compose materializes env there, baking `env_file:` entries into the generated override) and **before `launch_deploy`**, which is what puts the values in the very first container. Blank/omitted text leaves a stored file untouched, so a redeploy with an empty env box never silently wipes a project's environment; clearing stays `DELETE .../env`. The helper flushes and the caller commits: `upload_complete` commits explicitly (a manifest-less file sync never reaches a provisioning commit, and `get_db` does not commit on close), while git deploy lets its provisioning commit persist it so a failed clone rolls the env back together with the project row it also created.
- **The plugin-owned `{project_dir}/.env` is untouched.** That file is written by plugin `install.sh` scripts for compose `${VAR}` **interpolation**, which is a different thing from injecting into a container. When a project-level env file exists, `docker_service.compose_env_flags` passes `--env-file {project_dir}/.env --env-file {materialized}` so interpolation keeps working *and* picks up the stored values; with no env it emits no flag at all and compose's automatic `.env` pickup is unchanged. Repeated `--env-file` needs Docker Compose >= 2.24.

Key invariants that aren't obvious from a single file:

- **No parts.** The `Part` table and `/parts/{type}/...` endpoints are gone. Dockerfile projects store everything directly on the `Project` row; compose projects use `ComposeService` rows. The `parts` key never appears in API responses.
- **Two upload paths, one provisioning path; deploy auto-creates.** Files reach a project either via the legacy `POST /projects/{name}/upload` (`projects.py::upload`, `List[UploadFile]` multipart — each filename carries its path relative to the project root) or via the **chunked upload** trio used by `fhcli deploy <local-path>` and the web UI for large files/folders: `POST …/upload/chunk?upload_id=&offset=` (raw 1 MiB octet-stream pieces written at their offset into a staged zip under `{DATA_DIR}/uploads/{project}/{upload_id}.zip`), `POST …/upload/complete` (safe-unzip into the project dir — guarded member-by-member by `_safe_join` against zip-slip — then provision), and `DELETE …/upload/{upload_id}` (abort/cleanup). **None of these require the project to pre-exist** — `upload`/`upload_complete` call `projects.py::_get_or_create_project`, and `chunk`/`abort` only slug-validate the name (via `_staging_zip_path`) since the row is created on `complete`. There is no `POST /projects` create endpoint. 1 MiB pieces stay under nginx's 1 MB default body limit (the API vhost also sets `client_max_body_size 8m`). Both entry points recreate the tree under the single per-project dir (`PROJECTS_DIR/{name}`) and end in the shared `projects.py::_autoprovision` (`_detect_manifest` → `provision_compose` / `_provision_from_dockerfile`; compose wins over Dockerfile). When a manifest is provisioned the upload then **auto-launches build + run** via `projects.py::launch_deploy` (the single `deploy_mode →` docker_service dispatch, shared with git deploy and the non-interactive plugin install) and returns a `ws_path` (`WS /projects/{name}/deploy`, served by the shared `deploy_stream_session`) for the client to stream the deploy log live — exactly like `POST /git/add`. Both return `UploadResponse` (carrying `ws_path` + `job`); an upload with no manifest is a plain file sync (mode stays `pending`, no `ws_path`). There are no `/dockerfile`, `/compose`, or `/context` upload endpoints, and no per-mode `/build` or `/start` (`/compose/build`, `/compose/up`) endpoints — re-upload to redeploy.
- **Git is the other deploy transport** (`app/routers/git.py`). `POST /git/add` (body `{name, git_url, branch?}`) **gets-or-creates** the project row (idempotent: a new name creates it, an existing name redeploys it), wipes + `git clone --depth 1`s the repo into `PROJECTS_DIR/{name}` (`app/services/git_service.py`; HTTPS or `git@host:path`/`ssh://` URLs), then runs the **same** `projects.py::_autoprovision` as the upload flow (no manifest in the repo root → 400, changes rolled back + dir removed). It then auto-launches the build+run job via `launch_deploy` (a fresh blue/green version, so re-cloning redeploys) and returns a `PluginAddResponse` with `ws_path: /git/deploy/{name}`. `WS /git/deploy/{project}` is a read-only stream (no interactive prompts) that tails that job via `interactive_service.stream_job`, mirroring the non-interactive plugin install socket. Driven by `fhcli deploy <git-url>` (which dispatches to this route when SOURCE looks like a git URL) and the web UI's "+ deploy project" form's git tab (which reuses `InstallPane`). The `.git` dir is kept on disk (enables a future pull/update). **`/git/add` is admin-only** — it names the repository, so it is how an origin is set or changed.
- **The git origin is stored, and `POST /projects/{name}/redeploy` replays it.** A git deploy records `Project.git_url` + `Project.git_branch`, so a redeploy needs nothing but the project name. The clone → provision → launch sequence lives in **`projects.py::deploy_from_git`** (not in `git.py`, which already imports `projects.py` — the reverse would cycle, while `git_service` is a plain service both use); `git.py::add_git_project` and `redeploy_project` are both thin wrappers over it. `_autoprovision` **clears** the origin whenever it provisions, and `deploy_from_git` re-stamps it afterwards — so a file upload leaves it NULL and `redeploy` 400s ("not deployed from git") instead of silently re-cloning a stale repo; a manifest-less file sync provisions nothing and so leaves the origin alone. `ProjectResponse` carries the origin with any http(s) userinfo stripped (`projects.py::public_git_url` — an `https://<token>@host/…` PAT must not reach a guest's project list; an `ssh://git@host` login is not a secret and is kept).
- **SSH keys for private git repos** (`git_service.get_or_create_github_key`). `GET /git/key` returns the server's GitHub SSH public key so a user can add it to GitHub and clone private repos over `git@github.com:…`. It's read-or-create: the key is keyed off the `Host github.com` block in the server user's `~/.ssh/config` (one global key, `/root/.ssh` in production); when absent, an ed25519 keypair (`~/.ssh/freeholdy_github`) is generated via `ssh-keygen` and a matching config block written. The response (`GitKeyResponse`) carries the public key + GitHub "add this key" `instructions`. When a `POST /git/add` clone fails an SSH-auth check (`git_service.is_auth_failure`), the 400 detail is augmented to point the user at this endpoint — surfaced by both `fhcli get-git-key` and the web UI header's "git key" button (`GitKeyModal`).
- **One per-project directory.** Both modes store files under `PROJECTS_DIR/{name}` (resolved by `compose_service.project_dir`); the mode can't be known until the root is scanned, so files can't be split across mode-specific dirs.
- **`DELETE /projects/{name}` is a full teardown.** For dockerfile projects: `docker rm -f` **every** blue/green version's container + `docker rmi -f` every version's image (`_teardown_dockerfile` iterates `project.versions`, a superset of the active container/image). For compose projects: `docker compose down --rmi all` (removes containers, networks, *and* the current images) + removal of every retained `freeholdy_{name}_{svc}:v{N}` version tag (matched by prefix via `deploy_service.remove_all_compose_version_artifacts`, since `--rmi all` only sees the *current* compose files) + the `{DATA_DIR}/versions/{name}/` snapshots + `shutil.rmtree` the compose directory. Both modes then remove the nginx config, reload nginx, and delete the DB row (cascades to `ComposeService`). **Volumes go too, by default**: `delete_volumes` (query param, default **true**) removes every volume `volume_service.list_project_volumes` attributes to the project — resolved *before* teardown, because teardown destroys the compose file and the containers that are the only record of which volumes (anonymous ones especially) are the project's, and applied *after* it, because docker refuses to remove an in-use volume. `external: true` volumes are never removed. `?delete_volumes=false` keeps them, and a project later deployed under the same name picks them straight back up; either way every volume removed or kept is named in the response `details`.
- **Port allocation unions all three tables.** `projects.py::_next_port` checks `Project.local_port`, `ComposeService.local_port` (non-null — unexposed services have NULL ports), **and** `ProjectVersion.local_port` (non-null) so the two modes and the blue/green version containers never collide. A version's port is reserved (kept in its `ProjectVersion` row) while it is active or inactive, and freed (`local_port=NULL`) when it is demoted to archived.
- **Container port binding is `127.0.0.1:{local_port}` only** (`docker_service.start_container`). Public traffic must go through nginx; do not bind to `0.0.0.0`. Exception: non-HTTP ports a compose file binds itself (mailserver's SMTP/IMAP, jitsi-meet's UDP 10000) survive the override merge — the generated override only *adds* the loopback binding for exposed services, it never strips original `ports:` entries.
- **Restart policy is `unless-stopped`** — containers come back after host reboot without freeholdy doing anything.
- **A container's environment is fixed when it is created**, so every path that must apply the current env recreates rather than starts. `deploy_service._rollback_script` recreates an `inactive` version's container too (it does not `docker start` it), which is what keeps "a container start uses the current environment" true everywhere; the cost is the container's writable layer, which an `archived` rollback already discarded.
- **Container logs are a read-only snapshot that bypasses the job registry** (`app/routers/logs.py`, `docker_service.get_container_logs` / `compose_logs`). `GET /projects/{name}/logs?tail=N` returns what the *container* printed — `docker logs --tail N` for dockerfile mode, `docker compose logs --tail N` (whole stack, interleaved) for compose — and `.../services/{service}/logs` does one compose service. Distinct from `GET /projects/{name}/status`, which returns the last freeholdy **job**'s log (build/run/stop). These run synchronously and spawn no `DockerJob`, so tailing can never collide with a deploy tracked under the same job key; there is no follow/streaming variant (clients re-request). A missing container is a 404, not a 500.
- **Volumes are derived, never stored** (`app/services/volume_service.py`, `app/routers/volumes.py`). A project's volumes are recomputed from three sources on every request — the volume-type mounts of the project's own containers (`docker inspect -f '{{json .Mounts}}'`, the only source for a dockerfile project's *anonymous* volumes, which an image's `VOLUME` instruction creates at `docker run`), volumes carrying `com.docker.compose.project={name}` (whose `com.docker.compose.volume` label gives the friendly key, and which survive a stopped stack), and the compose file's top-level `volumes:` (declared-but-not-created, `external`, `name:` overrides). Nothing is written to the DB, so the feature needs no migration. **All volume I/O runs inside a helper container** (`settings.VOLUME_HELPER_IMAGE`, default `alpine`) — `docker run --rm -v {volume}:/v …` for `du -sb`, `tar cf -` and the wipe+extract restore. A host-path implementation via the volume's `Mountpoint` is not viable: `/var/lib/docker/volumes` is root-only, so it would work when freeholdy runs as root and fail everywhere else. Sizes are cached for 60s and a miss is measured on a background thread — `GET /projects` reports `size_status: "pending"` rather than blocking on a multi-gigabyte `du`, while `GET /projects/{name}/volumes` always waits for a number. **Transfers are chunked in both directions**, mirroring the project upload: `POST …/volumes/{v}/download` tars into `{DATA_DIR}/volumes/{project}/` and returns an id, `GET …/download/{id}?offset=&length=` serves raw pieces, `DELETE …/download/{id}` discards the staging copy (stale ones are swept after 6h); uploads use the same `upload/chunk?upload_id=&offset=` + `upload/complete` pair. **A restore is a job, not a request** (`deploy_service.volume_restore`): stop the containers → wipe + extract → start them again, registered under the project's own job key (`compose:{name}` / `freeholdy_{name}`) so `/status`, `/abort` and `WS /projects/{name}/deploy` work on it and it can never run concurrently with a deploy. Its dockerfile path deliberately `docker start`s the *same* container instead of recreating it the way `launch_restart` does — an anonymous volume belongs to the container that created it, so `docker rm` + `run` would attach a fresh empty one and orphan what was just restored. Every route resolves its volume through `volume_service.find_volume(project, name)` first, so a token can only reach volumes of a project it already has access to; the routes are `require_project_access` (a guest may manage its own project's data), while deleting volumes only happens through the admin-only project delete.
- **Auth tokens are stored as SHA-256 hashes** (`app/auth.py::hash_token`). The plaintext token only exists at generation time in `scripts/generate_token.py` or in the `POST /tokens` response; there is no recovery path.
- **Tokens carry a role, and authentication is separate from authorization** (`app/auth.py`). `require_token` only resolves the bearer token to an active `Token` row (`None` in DEBUG, which counts as admin) — it grants nothing. Routes declare one of two authorization dependencies instead: `require_admin`, or `require_project_access`, which picks the route's `project_name` **path** parameter up automatically and admits an admin or a `guest` token scoped to that exact project. A route that declares only `require_token` is open to guests, so the two routes that do (`GET /projects/` filters the list to a guest's own projects, and `GET /tokens/me`) each do their own check. `guest` tokens (`Token.role` + the `token_projects` association) may **redeploy** (`POST /projects/{n}/redeploy`, from that project's own stored git origin), restart, abort, read logs/status, manage env, list versions and roll back the projects in their scope; everything else is 403, and a cross-project attempt is indistinguishable from a nonexistent project. **The deploy endpoints that name a source — the four upload routes and `POST /git/add` — are admin-only**, so a guest can rebuild its projects from their own repos but can neither repoint them nor push them arbitrary files. Deleting a project unbinds it from every token that covered it (association rows only) and never deletes the token, which may still cover others; a guest whose scope empties still authenticates but can act on nothing. `PUT /tokens/{id}/projects` re-scopes a token in place, so a CI credential can be widened or narrowed without re-minting it.
- **WebSocket auth is the mirror image, and default-deny** (`app/services/ws_session.py`). `authenticate(ws)` admits admin tokens only — right for the two exec sockets and the plugin-install socket; `authenticate(ws, project=name)` also admits guest tokens scoped to that project, which is what the shared `deploy_stream_session` (`WS /projects/{n}/deploy` and `WS /git/deploy/{n}`) uses. Close codes: 4401 unknown/inactive token, **4403 valid token without permission**, 4404 not found, 4409 busy.
- **Token management is `app/routers/tokens.py`** (`POST|GET /tokens`, `PUT /tokens/{id}/projects`, `DELETE /tokens/{id}`, all admin-only; `GET /tokens/me` for any token, and the only one a guest may call — it is what the web UI and `fhcli whoami` read to decide what to show). `DELETE` refuses to revoke the caller's own token. Revocation is soft (`active=False`), matching `scripts/generate_token.py revoke`.
- **The service writes to `/etc/nginx/sites-{available,enabled}` and shells out to `nginx -s reload` and `certbot`.** In production it must run as root or with sudoers carve-outs; locally, expect `PermissionError` from `_write_config` unless those dirs are writable.
- **Nginx config filenames are namespaced `freeholdy_{project}.conf`** — one file per project. Dockerfile `/ssl` and Dockerfile-upload (if cert exists) both call `nginx_service.write_ssl_config` which rewrites the whole file.
- **WebSocket nginx headers** (`proxy_http_version 1.1; Upgrade $http_upgrade; Connection "upgrade"`) are emitted only for endpoints where `websocket=True` — set automatically by scanning the manifest text, not by a user flag.

## Data & filesystem layout

- SQLite at `{DATA_DIR}/freeholdy.db` (default `data/freeholdy.db`), schema auto-created on startup via `init_db()` in `app/main.py`'s lifespan. No migrations framework — schema changes mean editing `app/models/orm.py` and **deleting the DB** (no alter-table support). The one exception is the blue/green versioning columns/tables, which ship an idempotent `migrate_db.sh` (repo root, `sqlite3` CLI; self-checks, backfills existing dockerfile projects as active v1, makes `project_versions.image_name/container_name` nullable for compose versions, creates `project_env_files` for environment variables, adds `tokens.role` + the `token_projects` table for token roles (the role column's DEFAULT backfills every existing token as `admin`) and `projects.git_url`/`git_branch` for the git origin, run by `install.sh` on upgrades and by `update.sh` on every update — fatally there, unlike install.sh which only warns) so an existing DB survives those upgrades without a wipe.
- All project files (both modes) live under `{PROJECTS_DIR}/{project}/` — the uploaded tree, the `Dockerfile` or `docker-compose.yml`, and (compose) the generated `docker-compose.override.yml`. `DOCKERFILES_DIR`/`COMPOSE_DIR` still exist in config but are only referenced by compose-plugin `.env` seeding.
- Materialized environment files under `{DATA_DIR}/env/{project}/` — `_project.env` plus `svc-{service}.env`, regenerated from the DB at every deploy/restart and removed on teardown. Kept outside `PROJECTS_DIR` so a git redeploy or compose rollback can't wipe them, and out of build contexts and version snapshots.
- Staged volume archives under `{DATA_DIR}/volumes/{project}/` — `dl-{id}.tar` (a prepared download) and `up-{id}.tar` (an upload being assembled), both short-lived: a download is deleted when the client says so or after 6h, an upload when its restore job ends.
- Compose version snapshots under `{DATA_DIR}/versions/{project}/v{N}/` — a full copy of the project dir per deployed version (kept outside `PROJECTS_DIR` because git redeploys wipe the project dir), removed on prune/teardown.
- Local nginx config backups under `{NGINX_CONFIGS_DIR}`, then mirrored to `NGINX_SITES_AVAILABLE` with a symlink in `NGINX_SITES_ENABLED`.

All paths and the port range come from `app/config.py` (pydantic-settings, reads `.env`).

## Conventions worth following

- Routers return Pydantic response schemas from `app/models/schemas.py`; status strings follow `ok | error` for action endpoints and `running | exited | not_found | no_image | error` for container state (synthesized in `projects.py::_container_status`, not stored).
- Service-layer functions (`docker_service`, `nginx_service`) return `(success: bool, message_or_logs: str)` tuples rather than raising — the router decides the HTTP shape.
- Project names are validated as DNS-safe slugs (`^[a-z0-9][a-z0-9-]*[a-z0-9]$`) in `schemas.py`; assume that downstream when constructing subdomains or container names.
- `ProjectResponse` shape: dockerfile projects fill `container: ContainerInfo`, `services: []`; compose projects fill `container: null`, `services: [ServiceInfo, ...]`. A freshly-created project has `deploy_mode: "pending"` with `container: null` and `services: []` until its first provisioning upload.
